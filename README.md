# PEARL Robot Platform

Web app for managing the PEARL lab's robots (Franka, xArm, Tiago): inventory, availability, reservations with conflict checking, maintenance and fault reports, and experiment logs. German and English UI.

| Part | Stack |
|---|---|
| Backend | Python 3.13, FastAPI, SQLAlchemy 2, PostgreSQL (SQLite for development) |
| Frontend | React 19, TypeScript, Vite, FullCalendar, i18next, three.js (intro) |
| Deployment | Docker Compose (Postgres + API + nginx) |

**User guide:** [Deutsch](docs/BENUTZERHANDBUCH.md) · [English](docs/USER_GUIDE.md) · **API reference:** `/api/docs` (OpenAPI, generated by the running backend)

## Features

- **Inventory**: name, type, location, responsible person, documentation link, description.
- **Status**: `available`, `maintenance`, `defect`, `retired`, plus a derived `reserved` while a booking is running.
- **Reservations**: calendar (month/week/day), drag to book, drag/resize to move. Overlaps are rejected with HTTP 409, and the response includes the clashing bookings and the next free slot of the same length.
- **Maintenance and faults**: tickets with status (`open` → `in_progress` → `resolved`), assignee, and a full history of status changes and comments. A fault can mark the robot as defect right away; when the robot's last open ticket is resolved, it goes back to `available`.
- **Experiment logs** per robot: date, person, description, result.
- **Accounts**: local accounts, LDAP and/or single sign-on (OpenID Connect, e.g. TU-ID), with `admin` and `member` roles.
- **Notifications** (bonus): e-mail (SMTP) and Discord webhook. New faults go to the robot's responsible person, the admins and Discord; status changes go to the reporter; e-mail reminders before a reservation starts. Each channel is off until configured.
- **Live status** (bonus): each robot (or a small agent next to it, `tools/robot_agent.py`) reports state, battery and a message with its own API key. The UI shows online/offline and refreshes every 10 s.
- **Statistics** (bonus): utilisation per robot (share of lab hours Mon–Fri 08–18), booked hours per day, a weekday × hour heatmap, top users, mean time to resolve faults, experiment success rate.
- **QR codes** (bonus): printable labels per robot; scanning opens the robot's page.
- **Design**: glass UI over a blueprint drawing of a robot arm whose joints carry the coloured glows; the arm changes pose per page. Light and dark theme, adjustable glass opacity and blur. Before sign-in, a scroll-driven welcome story (Apple-style): a 3D research arm stands at a conveyor belt; for each of the four core features (inventory, live status, clash-free booking, maintenance & logs) a module rides in, the arm picks it up, holds it to the camera while the caption shows, and sets it on a display pedestal. Then the joints light up, the PEARL logo lands, and the 3D scene hands over to the blueprint arm behind the sign-in form. Scrolling back rewinds it; the arm's motion comes from inverse kinematics, so pick-up and set-down line up exactly. It renders at up to 4K, steps resolution down to hold the display's refresh rate, and is skipped for "reduce motion".

### Permissions

| Action | Who |
|---|---|
| Add/delete robots, manage users | admin |
| Edit robot status/location/description | admin, robot's responsible person |
| Reserve, report issues, write logs, comment | every member |
| Change/delete a reservation or log | its owner, admin |
| Change ticket status/assignee | admin, reporter, assignee, robot's responsible person |

## Development

Prerequisites: Python 3.12+ and Node 20+.

```bash
# Backend (http://localhost:8000, API docs at /api/docs)
cd backend
python -m venv .venv
.venv/Scripts/activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
python -m app.seed              # optional demo data
uvicorn app.main:app --reload

# Frontend (http://localhost:5173, proxies /api to the backend)
cd frontend
npm install
npm run dev
```

On first start an `admin` / `admin` account is created. Change the password, or set `ROBOTS_BOOTSTRAP_ADMIN_PASSWORD` before the first start.

### Database migrations

Schema changes go through Alembic. The app applies pending migrations on startup (`ROBOTS_AUTO_MIGRATE`). After changing `app/models.py`:

```bash
cd backend && alembic revision --autogenerate -m "what changed"
```

`tests/test_migrations.py` fails if models and migrations drift apart.

### Live status agent

An admin creates a key on the robot's page (Live status → Create key). On the robot PC:

```bash
python tools/robot_agent.py --url https://robots.example.org --robot 3 --key rbk_3_...
```

It reports every 30 s using only the Python standard library. `--ping <controller IP>` reports `controller_offline` when the robot's controller does not answer; for more detail adapt `read_status()` (ROS topic, vendor API).

### Single sign-on (TU-ID)

`tools/dev_oidc.py` is a stand-in OpenID provider with two test users, so the TU-ID button works on a laptop (`backend/.env` with `ROBOTS_OIDC_ISSUER=http://localhost:9000`, client `robot-hub-dev` / `dev-secret`). Never expose it on a network. For the real TU-ID the lab registers the app with HRZ, using the redirect URI `<PUBLIC_URL>/api/auth/oidc/callback`.

The sign-in bar shows the Athene head from TU Darmstadt's official logo (`frontend/public/tu-logo.svg`, taken from tu-darmstadt.de). Its use must be cleared with TU before going live.

### Welcome animation assets

- `frontend/public/models/fr3.glb`: the Franka Research 3, converted from Franka's official meshes ([franka_description](https://github.com/frankaemika/franka_description), Apache-2.0; license and notice next to it). The arm's kinematics in `frontend/src/intro/fr3.ts` come from the same package. To rebuild: download the package, then `node tools/convert_franka.mjs <path to franka_description>`. The mesh shows Franka's brand marking; whether we may show it publicly is worth confirming.
- `frontend/public/models/studio_small_09_1k.hdr`: studio lighting from [Poly Haven](https://polyhaven.com/a/studio_small_09) (CC0).

### Tests

```bash
cd backend && pytest          # API, permissions, conflicts, LDAP (mock directory); SQLite
cd frontend && npm test       # API client, forms, pages, translations, FR3 kinematics (Vitest + Testing Library)
```

**Against PostgreSQL** (what production uses), without Docker: `tools/pgtest` starts a throwaway Postgres 17 on port 54329.

```bash
cd tools/pgtest && npm install --ignore-scripts && npm start      # keep running
cd backend && ROBOTS_TEST_DATABASE_URL=postgresql+psycopg://robots:robots-test@localhost:54329/robots_test pytest
```

This also runs `test_concurrency.py`, which fires parallel bookings for the same slot and checks only one wins (row locks only exist on Postgres).

Dev helper: `http://localhost:5173/?introAt=2.5` freezes the intro at 2.5 s to inspect a single frame (development builds only).

## Deployment (e.g. Proxmox VM or LXC with Docker)

```bash
cp .env.example .env    # fill in: passwords, secret key, public URL, TU-ID / LDAP / mail / Discord values
docker compose up -d --build
```

The app is served on port `8080` (`HTTP_PORT`). Put it behind the lab's reverse proxy for HTTPS. Every `ROBOTS_*` line in `.env` reaches the backend.

Then check every connection with the real values (nothing is sent or changed unless asked):

```bash
docker compose exec backend python -m app.check_setup
docker compose exec backend python -m app.check_setup --ldap-user <tu-id> --mail-to <your address> --discord-test
python tools/smoke_test.py --url https://<hub address> --user admin --password <first admin password>
```

### Backups

The `backup` service writes a compressed SQL dump of the database when the stack starts and then every 24 hours, into `./backups` (set `BACKUP_DIR` to put them elsewhere, e.g. on a separate disk or a mounted share). Dumps older than `BACKUP_KEEP_DAYS` (default 14) are deleted. Copy the folder off the server regularly: a backup on the same disk does not survive the disk.

Restoring (replaces all data; stop the backend first so nobody writes meanwhile):

```bash
docker compose stop backend
docker compose exec -T db sh -c "dropdb -U robots robots && createdb -U robots robots"
gunzip -c backups/robots-YYYY-MM-DD_HHMM.sql.gz | docker compose exec -T db psql -q -U robots robots
docker compose start backend
```

### Checking the setup

`check_setup` tests the security settings, the database, the TU-ID provider (and prints the redirect URI HRZ must have), LDAP (with `--ldap-user`, a real sign-in; the password is asked for), mail login (with `--mail-to`, one test mail) and the Discord webhook (with `--discord-test`, one test post). `smoke_test.py` then signs in and reads every part of the API.

## Configuration

All backend settings are environment variables with the `ROBOTS_` prefix (see `backend/app/config.py`).

| Variable | Meaning |
|---|---|
| `ROBOTS_DATABASE_URL` | SQLAlchemy URL, e.g. `postgresql+psycopg://user:pw@db/robots` |
| `ROBOTS_SECRET_KEY` | Signs login tokens. Must be long and random in production |
| `ROBOTS_ACCESS_TOKEN_MINUTES` | Login lifetime (default 12 h) |
| `ROBOTS_BOOTSTRAP_ADMIN_USERNAME` / `_PASSWORD` | First admin, created only when there are no users yet |
| `ROBOTS_LDAP_URL` | e.g. `ldaps://ldap.example.org`. Empty = local accounts only |
| `ROBOTS_LDAP_USER_DN_TEMPLATE` | DN to bind as, `{username}` is replaced |
| `ROBOTS_LDAP_ADMIN_GROUP_DN` | Members of this group (via `memberOf`) become admins |

| `ROBOTS_PUBLIC_URL` | Address users open the app at (links in notifications, SSO redirect) |
| `ROBOTS_AUTO_MIGRATE` | Apply database migrations on startup (default `true`) |
| `ROBOTS_OIDC_ISSUER` | SSO provider, e.g. `https://login.example.org/realms/tu`. Empty = SSO off |
| `ROBOTS_OIDC_CLIENT_ID` / `_CLIENT_SECRET` | Client registered with the provider; redirect URI is `<PUBLIC_URL>/api/auth/oidc/callback` |
| `ROBOTS_OIDC_USERNAME_CLAIM` | Claim used as username (default `preferred_username`) |
| `ROBOTS_OIDC_ADMIN_GROUP` | Members of this group (in the `groups` claim) become admins |
| `ROBOTS_OIDC_BUTTON_LABEL` | Text on the sign-in button (default `TU-ID`) |
| `ROBOTS_SMTP_HOST` / `_PORT` / `_USER` / `_PASSWORD` / `_FROM` | Outgoing mail. Empty host = no e-mail |
| `ROBOTS_DISCORD_WEBHOOK_URL` | Discord channel webhook. Empty = no Discord |
| `ROBOTS_DISCORD_LANGUAGE` | Language of Discord posts, `de` (default) or `en`. E-mails go out in each person's own language (the DE/EN switch in the app); times are in lab time (Europe/Berlin) |
| `ROBOTS_MAX_RESERVATION_HOURS` | Longest booking a member may make (0 = no limit; admins are exempt) |
| `ROBOTS_MAX_ADVANCE_DAYS` | How far ahead members may book (0 = no limit) |
| `ROBOTS_REMINDER_MINUTES` | E-mail reminder this long before a reservation (default 30, 0 = off) |
| `ROBOTS_LIVE_TIMEOUT_SECONDS` | A robot counts as online if it reported within this time (default 90) |

LDAP users are created on their first successful login. SSO users likewise; an SSO identity never takes over a local account with the same name (it becomes `<name>@sso`). Local accounts always use their local password.
